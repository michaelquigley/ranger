# 2026-07-29 — document sections land

Continuation of yesterday's design session on `additional-schema-structures`. Both convention changes went into the grimoire's `software/conventions/roadmap-convention.md`, plus a third that arrived mid-session.

## the convention

A new `## The body` section states the split: the body is the prompt, everything above the first `##` heading is what an agent executes, and supporting material lives in named sections below it (`## why`, `## background`, vocabulary open). Sections are conventional, never validated — an item carrying none isn't malformed and the schema table is untouched.

A new `## Contribution by pull request` section describes the participation mode the note never had. The existing hard rules are written for an agent in the operator's tree, where the uncommitted diff is the review queue; a contributor with repo access whose commit *is* the proposal is a different mode, gated by the merge instead. Such an item is triaged in the PR, can land already in its lane rather than `inbox`, carries `source:` pointing at the PR, and never touches `order.yaml` — ranking stays local and post-merge.

The stock `AGENTS.md` paragraph picked up the body split. Ranger's own `AGENTS.md` doesn't carry that paragraph (it links the grimoire note instead), so nothing needed syncing here; repos that do carry it verbatim are a separate sweep.

## the spike correction

Michael corrected the tag vocabulary mid-session: `spike` in this practice is not a time-boxed investigation. It's a **modifier** riding alongside a kind tag — `[feature, spike]`, `[epic, spike]` — flagging work with unknowns that need discovery. It rarely stands alone. The note's definition had been wrong since it was written; every ranger card using `spike` was already using it correctly, so only the note was out of step. The vocabulary section now splits kinds (defect, documentation, enhancement, epic, feature, story) from the one modifier, and says explicitly that removing `spike` once unknowns are settled isn't policed — leaving it is normal, removing it is fine — so nobody infers a rule from the absence of one. Nothing in the code carries tag semantics; `labels.ts` only maps tags to colors.

## the modal

Presentation only, and smaller than expected: pure CSS, no TypeScript. Two tiers sized apart via sibling selectors over the single existing markdown tree — the prompt (`> *:not(h2):not(h2 ~ *)`) at 1.06em, everything from the first `h2` onward (`> h2 ~ *`) at 0.88em, behind a rule and under dimmed headings. First pass demoted only, leaving the prompt at baseline; Michael's read was that the gap wanted widening from both ends.

The consequence worth knowing: an item with no `##` sections is *all* prompt, so its whole body now renders at 1.06em. Every existing card gets slightly larger body text. That's consistent — the prompt renders at prompt size regardless of whether the card happens to carry sections — but it is a visible change to cards nobody edited. Scoping the bump to `:has(> h2)` would leave section-less cards untouched at the cost of the same prompt rendering at two different sizes depending on its neighbors; rejected as the more surprising of the two.

Splitting the body at the first `##` and rendering two `<Markdown>` trees was the obvious approach and was rejected for a real failure it introduces: a link reference definition (or GFM footnote) declared under one section and used in the other stops resolving across two independent trees. The CSS route also sidesteps having to track fenced code blocks so a `##` inside a fence isn't mistaken for a heading. The new rules must sit *after* the existing `.item-body h1, h2, h3` block — same specificity, so source order decides; there's a comment saying so.

Docs: README grew a body paragraph in the convention section and its modal sentence; `ui-and-serve.md`'s item-modal bullet carries the presented-not-parsed framing and the reference-definition reasoning; CHANGELOG entry under Unreleased as CHANGE.
