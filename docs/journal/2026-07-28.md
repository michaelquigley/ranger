# 2026-07-28 — the schema structures card, shaped down

Design session on the `additional-schema-structures` roadmap item, which arrived tagged `epic, spike` and asking how the card schema should accommodate two emergent needs: supporting material kept separate from the prompt, and back-and-forth on cross-team cards. It converged on no schema change at all.

The two needs turned out to be different shapes. Prompt-vs-supporting-material is a sectioning problem — one author, static, and the reader who cares is an agent about to execute. Back-and-forth is an accretion problem — multiple authors, chronological, and mostly process residue.

The sectioning half resolved to a body convention rather than frontmatter, on the standing house position `richer-log` already states: a field earns its way into the schema, and machine semantics never become a parsing rule over prose. The argument that usually forces schema — "a machine can't find the prompt without structure" — mostly evaporates here, because the primary reader of a card body is an LLM and an LLM reads a markdown heading natively. So: the prompt is the unmarked default (everything above the first `##`), supporting material sits in named sections below, and sections are conventional, never validated. Zero schema-table cost, zero malformed semantics, zero span mapping, and it extends to whatever structure comes next for a paragraph. The unmarked default beat an explicit `## prompt` because every existing card stays valid untouched and you'd end up implementing the unmarked rule anyway as the old-card fallback.

The accretion half was killed by a detail Michael supplied mid-session: cross-team means parties *with repo access*, contributing by pull request. That makes a file-resident thread untenable — every conversational turn would cost a PR round-trip. But the forge can't be the durable home either, since a resolution living only in a merged thread is invisible to the next agent that reads the file, and the convention's whole thesis is that the files are the truth. Michael's call: triage inbound roadmap PRs in the PR. The merge becomes the triage decision, a contributed card can land already in its lane, `order.yaml` stays out of contributor PRs entirely (ranking is local and post-merge), and the merged card carries `source: github:org/repo#N` — the existing field doing exactly the job it was defined for — so the shaping conversation stays one click from the file.

Two things surfaced along the way and are worth keeping. The roadmap convention has no description of the inbound-PR participation mode at all: its hard rules ("never commit roadmap changes unless directed") are written for an agent working in the operator's tree, and a contributor whose commit *is* the proposal is a second mode the note needs to name. And an idea floated early — a "blocked on reply" state or tag — was retired once the PR detail landed: an open PR already is that signal, in the forge where the other party is.

Grounding check that's worth remembering: board load reads every item file whole and holds a parsed `ItemDoc` with `Body()` available (`workspace.go:106`), so a body-derived board signal would cost a parsing rule, not I/O. That's the only thing that would make a "has open questions" card marker cheap later — the I/O objection doesn't apply, only the prose-parsing one.
